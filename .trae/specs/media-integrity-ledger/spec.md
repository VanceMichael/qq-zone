# 媒体完整性账本、离线核验与定点修复 - Product Requirements Document

## Overview
- **Summary**: 为个人相册、群相册、说说、留言板四类备份建立持久的媒体完整性账本：仅对真正完成并关闭的目标媒体文件登记稳定来源身份、实际相对路径、字节数与 SHA-256 内容摘要；提供不登录、不联网的本地核验入口（缺失 / 内容变更 / 未登记 / 未完成四类稳定结果）；用户显式选择后，仅对确认损坏或缺失的项按原备份类型的既有取源与重试链路定点重建，并支持修复计划跨运行续作；账本始终以原子方式切换，旧备份可显式建立「来源未验证」基线。
- **Purpose**: 备份盘被移动、文件被手工整理或异常断电后，用户能离线分辨本地照片/视频是否仍然可信，且修复过程不重写健康文件、不要求一次性跑完。
- **Target Users**: 使用本工具备份 QQ 空间相册/群相册/说说/留言板，并长期归档本地文件的个人用户。

## Goals
- 四类备份各有一份随备份目录走的持久账本，登记「完成态」媒体。
- 续传半成品、HLS 中间产物、失败项永远不会被标记为健康。
- 离线核验：无登录、无网络请求、不修改任何媒体文件和账本，四类结果分开、稳定呈现。
- 定点修复：只重建被确认损坏/缺失/未完成的项；健康文件不重写；修复中断后下次可继续。
- 账本写入原子化：取消、崩溃、写盘失败后，磁盘上始终保留一份完整可解析的旧账本。
- 无账本旧备份可由用户显式建立本地基线，且基线条目标记为「来源未验证」。
- 现有增量跳过、断点续传、失败项重试、任务记录、查看页全部继续可用；凡依据账本声称健康或跳过的媒体，路径与内容必须与账本一致。

## Non-Goals
- 不做云端对账：除用户显式发起的修复外，不与 QQ 空间服务器比对原件；核验阶段绝无网络请求。
- 不登记核心媒体之外的文件：头像（avatars）、查看页资源（assets/、index.html）、data/backup.json、raw 元数据页、album_metadata.json 均不登记，也不作为「未登记」报告。
- 不自动删除用户文件：修复时损坏文件只隔离不删除；未登记文件不自动清理、不自动重下。
- 不改造现有查看页的数据格式与交互。
- 不引入第三方新依赖（哈希使用 Go 标准库）。

## Background & Context

### 现有目录布局
- 个人相册：`storage/qzone/<目标QQ>/album/<相册名>[/YYYY/MM]/IMG_*|VID_*`
- 群相册：`storage/qzone/<登录QQ>/qun/<群号>/<相册名>[/YYYY/MM]/...`
- 说说：`storage/qzone/<目标QQ>/shuoshuo/`（`data/backup.json`、`media/YYYY/MM/`、`avatars/`、`index.html`、`assets/`、`raw/`）
- 留言板：`storage/qzone/<目标QQ>/liuyanban/`（结构同说说）
- 任务记录：`storage/tasks/<id>.json`；配置：`storage/config.json`

### 完成态/半成品信号（现状）
- 普通直链下载（`internal/net/http/http.go` 的 `Download`）：下载前写 `目标文件.resume.json` sidecar，完整落盘并通过大小核对后删除 sidecar；异常中断会留下「目标文件 + sidecar」的半成品。
- HLS 下载（`internal/net/http/hls.go` 的 `DownloadHLS`）：分片直接写入最终目标文件名，中断会留下同名半截文件且无 sidecar 标记。
- 只有 `Download`/`DownloadHLS` 返回 nil error 才代表文件真正完成并关闭。

### 稳定来源身份（现状可用字段）
- 个人相册：照片 JSON 的 `sloc`（本地文件名由 `MD5(sloc)` 派生），配合相册 `id`。
- 群相册：群号 + 相册 `id` + `sloc`。
- 说说/留言板：条目 `tid` + 媒体 `MoodMedia.ID`（空间侧 pic_id/视频 id）；`ID` 为空时以 `tid+ID+URL` 的 MD5 兜底（与现有文件名派生一致）。

## Functional Requirements

### FR-1 账本模型与存放位置
- 每个备份「域根」一份账本，位于域根下隐藏目录 `.integrity/ledger.json`：
  - 个人相册：`storage/qzone/<QQ>/album/.integrity/ledger.json`
  - 群相册：`storage/qzone/<登录QQ>/qun/<群号>/.integrity/ledger.json`
  - 说说：`storage/qzone/<QQ>/shuoshuo/.integrity/ledger.json`
  - 留言板：`storage/qzone/<QQ>/liuyanban/.integrity/ledger.json`
- 账本为单一 JSON，至少包含：结构版本、备份类型（album/group_album/shuoshuo/board）、归属 QQ、群号（群相册）、哈希算法名（sha256）、创建/更新时间、条目数组。
- 每条目至少包含：稳定来源身份 `source_id`、媒体类型（image/video/voice）、相对域根的 POSIX 风格相对路径 `rel_path`、字节数 `size`、SHA-256 摘要、来源是否已验证标志 `origin_verified`、创建/更新时间。
- 来源身份格式固定：
  - 个人相册：`album:<目标QQ>:<相册ID>:<sloc>`
  - 群相册：`group:<登录QQ>:<群号>:<相册ID>:<sloc>`
  - 说说：`shuoshuo:<目标QQ>:<tid>:<媒体ID>`；媒体 ID 为空时用 `shuoshuo:<目标QQ>:<tid>:url:<MD5(媒体URL)>`
  - 留言板：同上，前缀为 `board:`
  - 本地基线（无网络身份）：`local:<rel_path>`，且 `origin_verified=false`
- 同一来源身份在一本账本中只对应一条条目（按 source_id 去重 upsert）。

### FR-2 仅登记完成态
- 账本条目只在下载链路成功返回（文件写完、关闭、通过下载层既有完整性核对）后，对最终路径文件计算字节数与 SHA-256 再登记。
- 续传半成品（存在 `.resume.json`）、HLS 中间产物（`.part`）、失败项禁止写入账本、禁止被标记健康。
- HLS 下载必须先写临时文件 `<目标>.part`，全部分片写完并正常关闭后才改名为最终目标文件；失败则保留 `.part` 作为未完成标记，不得出现「最终文件名的半截 HLS 文件」。
- 账本登记时若同一相对路径上已有 `local:` 基线条目，新条目（空间身份、已验证）替换它。

### FR-3 账本原子提交
- 写账本采用「同目录临时文件写完整 → flush/sync → 原子 rename 覆盖」；崩溃、取消、写盘失败时，`ledger.json` 要么是上一份完整状态、要么是新的完整状态，绝不出现半截 JSON。
- 另保留 `ledger.bak` 作为最近一次完好版本；加载 `ledger.json` 失败时回退到 `ledger.bak`。两者都损坏时中止账本相关操作并明确报错，不得用空账本覆盖。
- 一次备份的提交边界：个人/群相册每完整跑完一个相册提交一次（该边界点新状态完整）；说说/留言板在整次备份正常结束时提交一次；修复在修复运行结束时提交一次。
- 用户取消时：未到提交边界的成果（如跑到一半的相册）不提交，上一份账本保持不变；这些已下载但未登记文件在下次核验中如实显示为「未登记」，不会被声称为健康。

### FR-4 在线备份与重试集成
- 个人相册、群相册、说说、留言板备份及各自失败重试成功后，按 FR-1/FR-2 登记账本（`origin_verified=true`，因为字节确实来自空间且下载后重新计算了摘要）。
- 增量模式下的跳过判定：
  - 账本中存在同一来源身份条目，且条目的 rel_path 指向的现存文件字节数与 SHA-256 均一致 → 允许跳过（相册跳过此路径不需要网络 HEAD）；
  - 条目存在但路径不存在、大小或摘要不一致 → 不得跳过，走正常下载/换源链路重建；
  - 账本不存在或该文件无条目 → 沿用现有跳过逻辑（相册 HEAD Content-Length 判定；说说/留言板「非空即跳过」），但不得据此写入或声称账本健康。
- 非增量（全量）相册备份在某相册完整跑完后，账本中该相册目录前缀下的旧条目以本次成果整体替换。
- 下载失败、重试失败的项不登记；已有的历史条目不因一次失败的下载尝试而被改写或删除（磁盘文件是否仍可信由离线核验判定）。
- 账本登记/核对所需的哈希计算必须流式进行，不得把大视频整体读入内存。

### FR-5 离线本地核验
- 主菜单提供无需登录即可进入的「完整性核验与修复」入口；核验过程不构造登录态、不发起任何网络请求。
- 自动发现本机四类备份域根，列出类型、归属账号/群、账本有无与条目数，供用户选择单个或全部核验。
- 对每条账本条目，按下列优先级分类，结果稳定（按 rel_path 排序、可重复运行）：
  1. 目标文件不存在 → **缺失**；
  2. 目标路径存在未完成标记（同名 `.resume.json` sidecar 或目标为/存在对应 `.part`）→ **未完成**；
  3. 字节数不一致 → **内容变更**；
  4. SHA-256 不一致 → **内容变更**；
  5. 全部一致 → 健康（单独统计，并区分「来源已验证 / 来源未验证」两个数）。
- 对磁盘的反向扫描（仅核心媒体范围）：
  - 个人/群相册域根：递归全部文件，排除 `.integrity/`、`album_metadata.json`、`*.resume.json`、`*.part`；
  - 说说/留言板域根：仅扫描 `media/` 目录，排除 `*.resume.json`、`*.part`；
  - 发现的未完成标记文件（.part / .resume.json）计入**未完成**；在管理范围内但账本无对应 rel_path 的媒体文件计入**未登记**。
- 终端分四段报告：缺失、内容变更、未登记、未完成；每段给出数量与明细（相对路径、条目来源、期望/实际大小或摘要差异），并给出健康统计。
- 核验只读：不修改、不移动、不删除任何媒体文件，不修改账本，不在备份目录内写报告文件（报告仅输出到终端）。

### FR-6 旧备份显式建立本地基线
- 对没有账本的域根，用户经明确确认（菜单二次确认，文案说明含义）后可建立本地基线。
- 基线扫描与 FR-5 相同的核心媒体范围：对每个现存且非未完成的文件计算 size 与 SHA-256，写入 `origin_verified=false`、`source_id=local:<rel_path>` 的条目。
- 未完成文件（.part/.resume.json 对应目标）不得纳入基线，单列提示。
- 基线建立过程中及其后的任何文案都不得声称当前字节已与空间原件核对；条目保持「来源未验证」，直到该文件未来确实经由成功的在线下载/修复（字节来自网络并重新摘要一致）才升级为 `origin_verified=true`。
- 已存在账本的域根不允许「重建基线」覆盖；对核验出的「未登记」文件可另行执行「纳入基线」，同样标记来源未验证。

### FR-7 修复计划与持久化
- 仅在用户于核验后选择「修复」（或在菜单选择继续既有修复）时，才在该域根写入 `.integrity/repair.json` 计划；计划在请求登录之前落盘。
- 计划项来自核验确认的缺失、内容变更、可定位来源的未完成项；未登记项不自动进入修复计划（用户可改为纳入基线）。
- 每个计划项记录：source_id、rel_path、原因（missing/changed/incomplete）、媒体类型，以及按类型的取源提示（相册：相册名/相册 ID；说说/留言板：tid、媒体 ID，必要时从本地 backup.json 补全）。无法确定空间来源的项（如只剩 local 身份的基线项）标记为不可自动修复，修复时跳过并明确报告。
- 计划的写入与更新同样采用原子替换。无登录凭证、网络失败、用户取消时，未解决的计划项必须保留；下次运行进入同一入口可发现并选择「继续修复」。
- 计划项修复成功后从计划中移除；失败则保留并记录最后错误原因。

### FR-8 定点修复执行
- 修复需要登录（群相册沿用现有群授权）；登录失败或用户取消时保留计划，不做任何文件改动。
- 修复只处理计划内的 rel_path：
  - 内容变更/未完成：先把现有文件（连同 sidecar/.part 标记）移动到 `.integrity/quarantine/<时间戳>/` 下并保留原相对路径结构，再重建；缺失项直接重建；
  - 健康文件、计划外文件一律不得删除、改写或重下（实际下载前仍经 FR-4 的账本一致性核对）。
- 重建必须走各备份类型的现有取源与重试链路：
  - 个人/群相册：隔离/清除计划文件后，以增量模式、相册白名单限定在受影响相册，复用 Spider 的列表拉取、多候选地址、视频换源、断点续传与重试；
  - 说说/留言板：从本地 backup.json 定位 tid+媒体，复用现有 `RetryFailed` 的详情刷新、候选地址、getinfo 换源链路，成功后照常重写 backup.json 与查看页。
- 修复成功的文件按 FR-2 重新登记（摘要一致、`origin_verified=true`）；修复结束时账本原子提交一次。
- 修复运行写入一条 mode=repair 的任务记录（统计与残留失败项），与既有任务记录体系并存；跨运行续作以 repair.json 为准。

### FR-9 菜单入口
- 主菜单新增「🧪 完整性核验与修复（本地核验无需登录）」，进入时不触发登录。
- 流程包含：选择域根 →（无账本时）建立基线或仅列文件 → 核验与四段报告 → 修复 / 纳入未登记项 / 继续未完成计划 / 丢弃计划 / 返回。
- 所有破坏性或外发动作（建立基线、隔离修复、丢弃计划）都必须有显式确认；核验本身不需要确认。

### FR-10 既有能力兼容
- 现有增量跳过、断点续传（含 sidecar 与 If-Range）、失败项重试菜单、任务记录、说说/留言板查看页行为保持可用。
- 查看页不读取也不依赖 `.integrity/`；账本目录对查看页、备份扫描无副作用。
- 全量（非增量）相册备份清空相册目录的行为不变，但账本域根位于相册目录的上一级，不会被一并清掉。

## Non-Functional Requirements
- **NFR-1 性能与内存**：哈希全部流式 SHA-256；核验大体积备份时显示进度，内存占用不随文件体积增长；跳过核对的本地哈希开销在可接受范围（本地磁盘顺序读取）。
- **NFR-2 跨平台**：路径处理兼容 macOS 与 Windows（原子 rename、路径分隔、隐藏目录），不改变现有 Windows 构建方式。
- **NFR-3 可测试性**：账本读写、分类决策、基线、计划续作、跳过决策等纯逻辑必须可在无网络、无登录条件下单测；`go build ./...`、`go vet ./...`、既有测试全部通过。
- **NFR-4 无新增依赖**：使用 Go 1.25 标准库与现有依赖完成。
- **NFR-5 可观测性**：核验/修复过程的关键结论与错误同时输出到终端和现有任务日志。

## Constraints
- **Technical**：Go 1.25；fx 依赖注入；下载层在 `internal/net/http`，备份编排位于 `internal/app`，交互位于 `internal/cli`；媒体下载链路需登录态与 Cookie，不得为核验引入任何网络调用。
- **Business**：用户数据安全优先：只读核验、隔离不删除、健康文件不重写、所有写动作可解释。
- **Dependencies**：修复链路依赖现有 qzone 客户端能力（登录、相册/照片列表、视频多源、说说/留言详情）；无凭证时只能停在计划阶段。

## Assumptions
- 进程工作目录即现有 `storage/` 所在目录（与现状一致），账本路径均相对该目录。
- 同一域根同一时刻只有一个备份/修复进程操作（沿用现状，不引入文件锁）。
- 异常断电后 POSIX 同目录 rename 的原子性成立；Windows 桌面版同样支持替换式 rename（实现上保证 temp 与目标同卷）。
- 现有 `*.resume.json` 命名与「成功后删除 sidecar」的行为保持不变，作为未完成检测信号之一。

## Acceptance Criteria

### AC-1: 四类备份各有结构正确的持久账本
- **Type**: `rule`
- **Given**: 任一类型的备份成功下载至少一个媒体文件
- **When**: 备份到达提交边界
- **Then**: 对应域根出现 `.integrity/ledger.json`，条目含 source_id（符合 FR-1 身份格式）、rel_path、size、sha256、origin_verified=true、时间戳；JSON 可被重新解析
- **Pass Condition**: 四类备份各构造一例，字段与身份格式断言通过
- **Evidence**: 新增单元测试断言 + 实际生成的 ledger.json 样例

### AC-2: 半成品、HLS 中间产物、失败项不会被标记健康
- **Type**: `rule`
- **Given**: 制造 `.resume.json` 半成品、`.part` 文件、下载失败项三类场景
- **When**: 备份提交账本 / 执行核验
- **Then**: 三类对象均不出现为账本健康条目；HLS 成功路径只在 rename 后产生最终文件，失败时只留 `.part`
- **Pass Condition**: 单元测试覆盖三种场景，且 hls.go 经临时文件+最终 rename 实现
- **Evidence**: 账本断言、临时目录文件树断言、hls 下载实现代码与测试

### AC-3: 账本原子切换，中断后始终存在可解析的上一份状态
- **Type**: `rule`
- **Given**: 已存在一份完好账本
- **When**: 新状态写入过程中模拟失败（磁盘写入错误/进程取消）
- **Then**: ledger.json 仍为上一份完整可解析内容；ledger.json 损坏时可从 ledger.bak 恢复；两份皆损时明确报错且不覆盖
- **Pass Condition**: 故障注入测试三种情形
- **Evidence**: atomic write/load 单元测试
